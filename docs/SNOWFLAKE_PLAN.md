# Snowflake 計算資源の使用計画（ACAC5）

作成 2026-11-04。使うのは **Snowflake のコンピュートプール**です（Kaggle GPU は使いません）。
この作業は CPU だけを使います（シミュレータとルールエージェント。ニューラルネットの学習はありません）。そのため GPU ノードの GPU 自体は使いません。

**方針（2026-11-04 決定）**：
- **CPU プール（SYSTEM_COMPUTE_POOL_CPU）を優先**します。使えない場合や混んでいる場合だけ GPU プールにします。
- 実行の開始は、改めて許可を得てからにします（現時点では計画の見直しのみ）。

## 0. 環境の確認結果（読み取りのみ。計算資源は未起動）

- Mac の Chrome から Snowsight（oryotul / ga_technologies、RIKU_OKAWA、ロール INVESTMENT_MANAGEMENT）を操作できることを確認しました。
- コンピュートプールは 2 つあります。

  | プール | インスタンス | vCPU / メモリ | 状態（確認時） | 最大ノード | 自動一時停止 | 料金（クレジット/時・ノード） |
  |---|---|---|---|---|---|---|
  | SYSTEM_COMPUTE_POOL_GPU | GPU_NV_S（A10G） | 6 / 28 GiB | 一時停止 | 50 | 10 分 | 0.57 |
  | SYSTEM_COMPUTE_POOL_CPU | CPU_X64_S | 3 / 13 GiB | 稼働中（他の 48 サービスと共用） | 150 | 10 分 | 0.11 |

  料金は Snowflake の Credit Consumption Table（表 1(f)）の値です。vCPU 1 個あたりでは CPU プールが 0.037、GPU プールが 0.095 で、**CPU プールの方が 2.6 倍安くなります**。
- レガシーノートブックは作成できません。**Workspace のノートブック**を使います。先例として casmi_scorer_a10g.ipynb があり、ステージ `@SNOWFLAKE_LEARNING_DB.CURSOR_MCP.CASMI_STAGE` から `session.file.get` で取り込む方式でした。GPU ノードでは nproc=8、メモリ 31 GB と表示されています。
- 外部ネットワークには接続できません。そのため全依存物をオフラインのバンドルにしました。

## 1. 2 つの資料の原則と、この計画での対応

| 原則 | この計画での対応 |
|---|---|
| アルゴリズムが先。計測してから最適化する | 1 試合（451 秒）の内訳を計測済みです。シミュレータ本体 14.5 秒、エージェント 11.3 秒、import 7.5 秒、合計約 40 秒です。1 コアで毎時 90 試合を確認しました。 |
| タスク並列 | 1 試合 = 1 プロセスです（プロセスを再利用すると結果が変わるため）。ノード内は全 vCPU を使い、ノード間はジョブ表を `--shard i/k` で分割します。 |
| 使わないときはセッションを止める | 編集とデバッグはすべてローカルの CPU で済ませました。ノートブックには、事前に用意した 3 セルを貼るだけにします。実行が終わったらすぐ切断し、プール画面でアクティブノードが 0 になったことを確認します。 |
| CPU で動作確認してから本番 | ローカルでバンドルを新規展開し、同梱の Python 3.10 で構築しました。同じ seed で結果が一致することを確認済みです（下記）。 |
| 小規模テストを先に | Phase 1（12 試合、1 ノード）で、処理速度・決定性・環境を確認します。合格した場合のみ Phase 2 に進みます。 |
| 時間上限と早期終了 | 予算の上限を三重に設けます。① snowrun の `--budget-min` を過ぎたら新しい試合を始めない。② 実行中の試合も 10 分後に打ち切る。③ ノートブック側で予算＋12 分の時点で強制終了する。Phase 2 は全比較を同時に進め、区切りごとに analyze.py で停止を判定します。 |
| チェックポイント | 結果を 1 試合ごとに追記します。同じコマンドを再実行すると続きから再開します。ステージへは 5 分ごとにコピーします。 |
| 計測してから最適化する（追加の検証） | forkserver 方式（シミュレータを 1 回だけ import し、試合ごとに新しいプロセスを fork する）を試しました。4 試合で spawn 72.7 秒に対し forkserver 74.9 秒で、**速くなりませんでした**（結果は完全に一致）。1 試合あたりの起動費用はすでに小さく、時間の大半はシミュレータ本体とエージェントの計算です。そのため既定は spawn のままにします。 |
| 利用率の計測 | 30 秒ごとに結果件数とロードアベレージを出力します。cgroup の割当（cpu.max）からワーカー数を自動で決めます。 |
| 予算を事前に配分する | 下の表のとおりです。 |

## 2. ローカルで済ませた準備（計算資源の使用 0）

- **オフラインのバンドル** `acac5pack.tar`（164 MB、sha256 の先頭 f5b32819d2a78342）。9.5 MB ずつ 18 分割して Chrome からアップロードします。
  - シミュレータの新しい wheel（11/04 版）、lightgbm 4.5.0、scipy、numpy などの wheel。
  - **持ち運べる CPython 3.10**（26 MB）。ランタイムに Python 3.10 がなくても動きます。シミュレータの .so が cp310 のためです。
  - エージェント（v15w、v17e、比較相手の各版）と、ジョブ表 phase1（12 試合）、phase2（1536 試合）。
  - ray を入れずに動かすためのパッチ（patch_noray.py）。
- **node_setup.sh**：venv の作成、オフラインでのインストール、import の確認、使える CPU 数の表示。新規の環境で 16 秒でした。
- **snowrun.py**：一括実行（並列、予算、再開、shard）。**nb_driver.py**：ノートブック側の監視（進捗、ステージへの保存、強制終了、決定性の照合）。**analyze.py**：shard の結果をまとめ、停止規則で判定します。
- **確認済みのこと**：同梱の Python で新規構築した環境で、det_v17_v15 の seed 41000（赤・青）がローカルの値と完全に一致しました（loss 0.1714 / 589 秒、win 0.95 / 876 秒）。2 ワーカーで毎時 189 試合です。

## 3. 段階と予算

速度は控えめに **vCPU 1 個あたり毎時 60〜90 試合**と見積もります。vCPU がハイパースレッドの場合を見込んだ値です。GPU_NV_S なら毎時 360〜540 試合、CPU_X64_S なら毎時 180〜270 試合になります。

| 段階 | 内容 | ノード | 実時間 | ノード時間（起動・構築・停止待ち 10 分を含む） | GPU プール | CPU プール |
|---|---|---|---|---|---|---|
| 0 | ステージへのアップロード（18 ファイル）。UI 操作のみ | 0 | 約 15 分 | 0 | 0 | 0 |
| 1 | 小規模テスト：構築、決定性 6 試合、p2 相手 6 試合 | 1 | 約 12 分 | ≤0.35 h | ≤0.2 cr | ≤0.04 cr |
| 2 | 本評価：v17 対 v15 を 384 試合、6 種の相手 × v15/v17 × 96 試合 | **6（CPU、既定）**または 3（GPU） | 約 70 分（早期終了なら約 35 分） | GPU 約 4.2 h ／ CPU 約 8.3 h | ≤2.4 cr | ≤0.9 cr |
| 3 | 候補の一括探索（例：20 設定 × 8 相手 × 48 試合）と戦術選択器の学習 | 別途 | | | **別途承認** | |

**上限**：Phase 1 と Phase 2 の合計を **GPU プールなら 3 クレジット、CPU プールなら 1.2 クレジット**までとします。超えそうな場合はその時点で止めて報告します。

### Phase 1 の合格条件（1 つでも外れたら Phase 2 に進まず、ローカルで直す）

1. node_setup が成功する（Python 3.10 か同梱版、GLIBC 2.34 以上）。
2. `check_det`：決定性 6 試合がローカルと完全一致する。
3. エラーが 0 件。
4. 速度が毎時 300 試合以上（GPU ノード）または毎時 150 試合以上（CPU ノード）で、ロードアベレージがワーカー数に近い。

### Phase 2 の停止規則

ジョブは `(idx//16, tag)` の順に並べてあります。そのため、どの比較も同じ割合で進みます。16 試合の区切りごとに、ステージの結果を `analyze.py` で判定します。

- 次のいずれかがすべての比較で成り立てば、その時点で全ノードを止めます。
  - 95% 信頼区間が 0（直接対決では 0.5）を含まない。
  - 信頼区間の幅が ±0.05 未満。
- 結果は v15 と v17 の選択と、相手の型ごとの弱点の特定に使います。弱点は Phase 3 の候補設計の入力になります。

## 4. 実際の手順（ノードを起動する時間を最短にするため）

1. （ノード不要）Snowsight でステージ `CASMI_STAGE/acac5/pack/` に 18 ファイルと sha256 をアップロードします。既存ステージの下のフォルダを使うので、新しいオブジェクトは作りません。
2. 新しいノートブック acac5_runner.ipynb を作ります。セルの内容は前もって作っておいたものを貼るだけです。設定ではプールを選び、**アイドルタイムアウトを最短**にします。
3. 接続（ここから課金）したら、次の 3 セルを順に実行します。
   - セル 1：`session.file.get` → 結合 → sha256 確認 → 展開 → `bash node_setup.sh`（約 3 分）。
   - セル 2：`D.run(session, STAGE, 'phase1', budget_min=8)` と `D.check_det(...)`。
   - セル 3（合格時のみ）：Phase 2 の shard 0 を実行します。ほかのノードは同じノートブックを複製して shard 1、2 を実行します。
4. 終了したらすぐに**ノートブックを切断**し、コンピュートプール画面でアクティブノードが減ったことを確認します。プールが 10 分後に自動で一時停止する分の課金は避けられません（プールの所有者は ACCOUNTADMIN のため、設定は変えません）。
5. 結果をステージからダウンロードし、ローカルで解析します。そのあと GitHub と FIELD_ANALYSIS.md に反映します。

## 5. リスクと対策

| リスク | 対策 |
|---|---|
| ランタイムが Python 3.10 でない | 同梱の CPython 3.10 を自動で使います |
| GLIBC が古い（2.34 未満） | Phase 1 の最初の出力で判明します。そうなれば中止し、ローカルで別の構成を用意します |
| 共用の CPU プールが混んでいて起動しない（"insufficient capacity"） | GPU プールに切り替えます |
| ブラウザが切断される | 結果は 5 分ごとにステージへ保存されます。再実行すると続きから再開します |
| 試合が終わらない | 予算の上限を三重に設けています |
| 規約 | シミュレータの配布物は社内ステージにのみ置きます。GitHub には wheel を載せません |

## 6. 実行記録（2026-11-05）

| 段階 | 結果 |
|---|---|
| 0 アップロード | 18 分割（9.5 MB ずつ）と sha256 を `CASMI_STAGE/acac5/pack/` に置いた。Chrome の file_upload は 1 回 10 MB まで。読み込めるのはスクラッチパッド上のファイルだけ（outputs は不可）。ステージのダイアログは下端が画面外に出るため、Tab キーで「アップロード」を選んで Enter で押す |
| GPU プール | ノートブックの「接続」を押すと、前回の CASMI_A10G サービス（GPU）に自動でつながった。10 分以内にノードが割り当てられず、Snowflake 側で自動的に取り消された（課金されたノード時間はなし）。**今後はドロップダウンの「新しいサービスを作成」から CPU プールを明示的に選ぶ** |
| CPU ノード | CPU_X64_S 1 台は nproc=4、メモリ 15 GB、Xeon Platinum 8375C。cgroup は v1 で cpu.max はない。プールに空きノードがあれば接続は約 30 秒 |
| 問題 1 | 同梱 Python の `sysconfig LIBDIR` がビルド時のパスを指しており、`libpython3.10.so.1.0` が見つからなかった。`readlink -f $PY` から求めるよう修正した。ローカルではそのビルド時のパスが偶然存在したため、気づけなかった |
| 問題 2 | スレッドの過剰な起動：OpenMP/BLAS が 1 試合に 4 本ずつスレッドを立てて競合していた（sys 25%、ロード 12）。**`OMP/OPENBLAS/MKL_NUM_THREADS=1` で毎時 60 試合 → 173〜190 試合（1 ノード）** |
| 問題 3 | 決定性：OpenBLAS のカーネルがノードでは SkylakeX、ローカルでは Prescott だった。カーネルが違うと丸め誤差が変わり、試合が分岐する。`OPENBLAS_CORETYPE=Prescott` に固定するとローカルと完全に一致した。逆にローカルで SkylakeX にすると、ノードの結果を完全に再現できた。スレッド数を 1 にすると、同じノードでは何度実行しても同じ結果になる |
| 速度の代償 | **なし**。Prescott で実行した本評価は、ノード 1 台あたり毎時約 175 試合で、SkylakeX と同等だった（毎時 120 という途中の見積もりは、ステージへの保存が 5 分遅れることを見落とした誤り）。そのため既定は Prescott のままとし、`ACAC_EXACT_BLAS=0` で解除できるようにした |
| 2 本番評価 | CPU ノード 6 台で **1496 / 1536 試合**を実行した（12:33〜14:12、各ノード約 85 分）。各ノードはステージのクレーム用ファイルを使い、空いている分担を自動で取った。全サービスは終了直後に「サービスとジョブ」画面から手動で一時停止した |
| 費用 | ノード時間は約 9.4 時間（Phase 1 を含む）× 0.11 で、**約 1.0 クレジット**（上限 1.2 以内）。GPU プールはノードが割り当てられず、0 だった |
| 運用の注意 | Mac がスリープすると Chrome の拡張機能が切断される（ノード側の処理は継続する）。ノートブックのセルの出力は再接続後に更新されなくなるが、ターミナルとステージの結果は正しい。進み具合は、ノードのターミナルから `python3 /tmp/peek.py` でステージの全分担の結果を取り込み、`analyze.py` で見る（warehouse は使わない） |

**大会への含意**：公式の評価環境も CPU の種類が違えば同じ試合にはならない（BLAS のカーネルの違いによる）。ローカルで再現できない勝ち負けを、seed 単位で細かく合わせ込んでも意味がない。平均で強いことが重要になる。
